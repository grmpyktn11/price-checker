Shopper · technical walkthrough

Inside a Shopper Search

One sentence in, five ranked products out, about 80 seconds later. Every step, every payload, every row written.

§

The pieces

A Python backend (FastAPI, port 8000) does the work. A React frontend (Vite, port 5173) is the UI. The frontend never calls a retailer or Claude directly — it only calls the backend. In development Vite proxies /api to port 8000, so both are the same origin and no CORS is needed.

Storage is one SQLite file, app.db, resolved from the repo root rather than the working directory. Nine tables. Every one appears below at the point it is written.

There are no migrations — Base.metadata.create_all() runs at import. New tables appear on restart; new columns on existing tables do not.

01instant

The request

POST /api/chat/message

{
  "conversation_id": "8f2a-…",   // crypto.randomUUID() in the browser
  "message": "i want a wireless mouse under 40 dollars"
}

The backend loads or creates the conversation row. History is stored as JSON, not one row per turn, because the app only ever reads or writes a whole conversation.

table · conversations 
id            VARCHAR  PK   // client-generated, not an autoincrement
history_json  VARCHAR       // [{"role":"user","content":"…"}, …] oldest first
criteria_json VARCHAR       // set once extraction succeeds
results_json  VARCHAR       // what /chat/decision needs, indexed by product_id
created_at    DATETIME
updated_at    DATETIME

Timestamps are naive UTC. SQLite stores no offset and reads back naive, so writing an aware value would make stored and read values different types.

02~2s

Sentence to criteria

model call · claude-sonnet-4-5 · 1000 max tokens The whole history plus the new message. Two possible reply shapes.

reply A — needs more information

{"type": "followup", "question": "What is your budget?"}

Turn ends. The question is appended to history, saved, returned. No search, no cost beyond this call. This is why a first message often gets a question back.

reply B — the criteria

{"type": "criteria", "criteria": {
  "name": "wireless mouse",          // the search-box string
  "category": "electronics",         // picks the subreddit list later
  "keywords": ["wireless"],          // extra search terms
  "must_haves": [                    // hard rules
    {"field": "Battery Capacity", "op": ">=", "value": 20000}
  ],
  "preferred_specs": [],             // same shape, soft
  "nice_to_haves": ["compact"],      // subjective phrases
  "budget_max": 40.0,                // penalty, never a filter
  "target_price": null,              // alert threshold only
  "fulfillment_preference": "either",
  "radius_miles": 25,
  "min_review_count": 5
}}

op is one of >= <= == contains exists. field is the spec name as a retailer prints it — no unit conversion happens later, so "20000" must be in the retailer's unit.

Then normalize() replaces explicit nulls: radius_miles → 25, min_review_count → 5, the four list fields → []. It replaces nulls, not just missing keys — the model emits null, and a None reaching a comparison downstream raised a TypeError that got swallowed and looked like a retailer outage.

Location gate

lat FLOAT
lon FLOAT

No lat/lon → 400, and the turn just appended is not saved. Leaving a user message with no assistant reply would put two user turns in a row in the next prompt.

04~1s

Nearest stores

One Google Places searchText call per retailer that has stores, cached on rounded coordinates. Returns miles: 

{"target": 1.07, "bestbuy": 0.57, "microcenter": 12.4}

Score is max(0, 1 − miles / radius_miles). Amazon, a retailer with nothing nearby, and a failed lookup all get a neutral 0.5.

Per retailer, not per product. Shopper knows a Best Buy is 0.6 miles away. It cannot know whether that store stocks that mouse — no retailer publishes it.
0527.2s

Four retailers, concurrently

asyncio.gather over all four. The stage costs the slowest, not the sum — sequentially this was 63s of an 115s search.

RetailerTransportMeasuredState
Targethttpx → redsky JSON endpoints3.7sNo browser. 403s for hours, then relents.
Micro CenterPlaywright, server-rendered HTML23.0sNo bot wall. Publishes Mfr Part#.
Best BuyPlaywright, JS-hydrated24.4sSearch OK. Product pages Akamai-blocked.

Every scraper returns this exact shape

{
  "name": "Logitech M317 Mouse - Blue Aurora",
  "url": "https://www.target.com/p/-/A-79370051",
  "price": 11.99,
  "in_stock": true,        // null = the tile did not say
  "store_id": null,        // search is national inventory
  "distance_miles": null,
  "rating": 4.38,          // off the SEARCH tile, not the product page
  "review_count": 392
}

Ratings coming from the search page is the reason cards have ratings at all. They used to be read from the product page — the page Best Buy blocks and Amazon throttles first — so most cards said "no rating found". All four print it on the search results.

Top 3 per retailer survive. Each then gets its product page opened for specs, returned as a flat dict of retailer strings: 

{"Type": "Mechanical", "Mfr Part#": "WOMIER SK80 BLA", "Switches": "…"}
model calls 2–4 · spec recovery · max 3 per search Page loaded but no spec table found → raw page text plus the wanted field names goes to Claude. Capped so one retailer with broken markup cannot send a 12,000-character page per product forever. The cap is a shared budget object, not an int, or each concurrent retailer would get the full allowance.

every search records an outcome

OK rows parsed · OK_BUT_EMPTY answered, genuinely nothing · BLOCKED captcha/403/challenge · SELECTORS_RETURNED_NOTHING real page, parser found nothing — our bug · ERROR threw before parsing

Never collapsed into "failed": they need different fixes, and only the first two mean the retailer actually answered.

069.8s

Qualification, fit and identity

Up to 12 products. One call judges all of them.

payload sent

{
  "requirements": {
    "product": "wireless mouse",
    "keywords": ["wireless", "rgb"],
    "required_specs": [],  "preferred_specs": [],  "nice_to_haves": ["compact"]
  },
  "products": [
    {"index": 0, "retailer": "bestbuy", "title": "CORSAIR M75 …",
     "price": 52.99, "url": "https://…", "specs": {}}
  ]
}

reply, index-aligned

{"products": [
  {"index": 0, "qualifies": true, "spec_fit": 1.0, "nice_fit": 0.5,
   "group": "g1", "reason": ""}
]}

A malformed or partial reply leaves unjudged products at a neutral default rather than dropping them. Only an explicit false disqualifies.

What qualifies means

  • A stated quantity is strict. 2,000mAh fails a 20,000mAh request; so does 10,000.
  • A stated feature is strict when the product plainly lacks it — a $9 own-brand mouse has no RGB whether or not the title says so.
  • Unclear is not absent. A gaming mouse whose title omits RGB is kept; the doubt goes into spec_fit.
  • Vague wording ("compact", "good for travel") never disqualifies.

What group does

Same model at two shops, and the same model in another colour, share a group id. Two consequences.

Inheritance. A candidate with no first-party rating takes the best-supported rating in its group, tagged "amazon_inherited" and shown as "borrowed" on the card. Specs inherit the same way. Both take a ×0.9 penalty — the identity came from a model reading two titles, which is weaker than a part number.

Deduplication. Only the best-scoring listing in a group is returned; the rest ride along as variants. Ungrouped candidates are never collapsed — no group means the model said nothing about identity, which is not evidence.

07instant

The in-memory object

Everything from here operates on this. It is never persisted as-is.

RankedProduct(
  product = {…the 8-key scraper dict…},
  retailer = "bestbuy",
  specs = {"Type": "Mechanical", …},
  reviews = [                       // one dict per source
    {"source": "bestbuy", "rating": 4.4, "review_count": 965,
     "verified_ratio": None, "rating_distribution": None,
     "authenticity_flag": "ok"},
    {"source": "reddit", "rating": None, "review_count": None,
     "mention_count": 8, "url": "https://…", "summary_text": "…"}
  ],
  spec_match = 1.0,  review_score = 0.89,  price_score = 1.0,
  distance_score = 0.98,  nice_to_have_score = 0.5,  final_score = 0.92,
  specs_inherited_from = None,  group = "g1",
  sentiment = "positive",  sentiment_summary = "…",
  variants = [{"name": "…White", "url": "…", "price": 60.09, "retailer": "bestbuy"}]
)

The weights

spec_match35% review_score25% price_score20% distance_score10% nice_to_have10%

price_score is relative to this search. Cheapest 1.0, dearest 0.0 — unless the whole set is within 5% of the cheapest, then everything scores 1.0. Without that, $60.04 and $60.09 scored 1.0 and 0.0: the full price weight for five cents. Over budget multiplies by budget_max / price — a penalty, not a filter.

review_score is rating/5 scaled by confidence, where confidence is log10(1+count) / log10(1001) — 1,000 reviews is full trust. No rating anywhere gives a neutral 0.5, because a missing feed is not a bad product.

0827.5s

Per-product research

The top 5 each get their own Reddit search on their own name. Not one shared search for the category — that is the whole point. 

GET https://www.reddit.com/r/{subreddits}/search.rss
    ?q={product name}&restrict_sr=1&sort=relevance&t=year

Subreddits come from category, up to 4 joined into one multireddit path so a category still costs one request. 10 posts per query, each body clipped to 600 characters. No key needed — it is the public RSS feed.

Sequential, 2s apart, with one retry after 4s if a search returns nothing. Reddit 429s most requests from this host; hurrying gets everything refused. This is the single largest remaining block of the wait.

A result appends one row to that product's reviews list:

{"source": "reddit", "rating": None, "review_count": None,
 "mention_count": 8,          // threads found; NOT a review count
 "url": "https://reddit.com/…",
 "summary_text": "[r/MouseReview] …",
 "authenticity_flag": "ok"}

rating and review_count are deliberately null: a count of threads is not a count of reviews, and the review floor must not see it as one.

0910.9s

Reading the discussion, and the tie-break

payload — one entry per researched product

[{"name": "CORSAIR M75 …", "rating": 4.4,
  "discussion": "[reddit] …\n\n[youtube] …"}]
model call · sentiment 
{"products": [
   {"index": 0, "sentiment": "positive",   // positive|negative|mixed|unknown
    "confidence": 0.8, "summary": "one sentence"}
 ],
 "too_close": [0, 1]}   // ranked positions it cannot separate; [] = decisive

too_close empty → done, zero YouTube quota spent. Non-empty → the top 2 get a YouTube search (100 of ~10,000 daily units each) and the same call runs again with the extra evidence. That is exactly why the Video button is on some cards and not others.

The sentiment also cross-checks the stars. Negative talk against a rating ≥ 4.3, or positive talk against ≤ 3.5, flags the review row mixed_signal and cuts review_score by 15%. A star distribution that is over 80% five-star with under 10% in the 2–4 band flags skewed_distribution and cuts 25%.

10instant

Re-rank, collapse, filter

Scores recompute (research moved review_score), the list re-sorts, groups collapse to one listing each, then the review floor applies.

No count is not zero. evidence_count returns None when no source reported anything, and the floor skips those. Reading a blocked page's silence as "0 reviews" deleted the only RGB mice in an RGB search.
11~0.8s

Narration

model call · narration · 500 max tokens Top 5 with scores and evidence in, 2–4 plain sentences out. No markdown, no lists, no invented details.

If no retailer answered, the model is skipped entirely and a written-in-code sentence says the search did not run. "Nothing matched" is a claim about the market, and nothing was learned about the market.

table · conversations · write 
history_json  += user turn + assistant narration
criteria_json  = the criteria object from step 02
results_json   = [{name, url, price, in_stock, store_id,
                   distance_miles, retailer, reviews}, …]  // top 5, by index

Scores are not stored — the client already has them from the response. The index into results_json is the product_id a Track click sends back.

The trace, polled live while all of the above runs

GET /api/chat/progress/{conversation_id} — every ~900ms

{"running": true, "stage": "collect_candidates", "elapsed_ms": 15230,
 "retailers": [{"retailer": "bestbuy", "outcome": "SEARCHING", "candidates_kept": null},
               {"retailer": "target",  "outcome": "OK",        "candidates_kept": 3}],

{"running": false} is the stop signal. All four retailers appear immediately as SEARCHING because with them concurrent nothing reports for 25 seconds. It reads the same trace object the run is filling in, so the waiting screen cannot disagree with the debug panel.

The full debug block carries every search URL, page size, raw row count, per-stage milliseconds, every dropped candidate with its reason, and the too_close verdict. In memory only, last 5 runs, gone on restart.

13instant

Track

POST /api/chat/decision

{"conversation_id": "8f2a-…", "product_id": 0, "decision": "watch"}

Four tables written in one transaction. This is the only path that persists a product.

tables · items → listings → price_history → reviews 
items      id PK, name, category, criteria_json, budget_max, target_price,
           fulfillment_preference, radius_miles, min_review_count,
           status ("watching"|"archived"), created_at

listings   id PK, item_id FK, retailer, store_id, store_name, distance_miles,
           url, price, in_stock, shipping_days_est, scraped_at
           UNIQUE(item_id, retailer, store_id, url)

price_history  id PK, listing_id FK, price, recorded_at

reviews    id PK, item_id FK, source, rating, review_count, verified_ratio,
           rating_distribution_json, authenticity_flag, url,
           summary_text, fetched_at

A product with no URL is refused: the listings unique key is meaningless without one and a rescan could never re-find it.

14ongoing

The background jobs

APScheduler, in-process, started with the server.

JobScheduleDoes
scrapeevery 6hRe-run the pipeline per watched item; upsert listings; a changed price appends a price_history row.
review_checkcron 03:00Find alternatives cheaper than anything already stored. Max 3 alerts per item per run.
digestcron 08:00Email every alert with sent_at IS NULL, then stamp them.
table · alerts 
id PK, item_id FK, listing_id FK,
reason ("price_drop"|"target_hit"|"new_alternative"),
sent_at DATETIME   // NULL = queued for the digest

Only target_hit emails immediately. The cheaper-than-anything-stored rule and the cap exist because a rescan across four retailers finds ~20 URLs it has not seen before, and alerting on each sent 21 notices about one USB hub in a single email.

The other flow: projects

Paste a Claude conversation at /api/projects/import. One model call extracts a shopping list; each ticked item runs the same pipeline sequentially, 5 per run, with research_top_n=0 so no Reddit or YouTube quota is spent.

tables · projects, project_items 
projects       id PK, name, source ("paste"|"share_link"), source_url,
               created_at, updated_at

project_items  id PK, project_id FK, name, why, criteria_json, quantity,
               essential, selected,
               status ("pending"|"searching"|"done"|"failed"),
               results_json, error, searched_at

results_json holds ProductOut-shaped dicts — run_pipeline persists nothing itself, so without it the page would be empty after a reload.
